# Logs

Every API log is one JSON line on stdout, and every request, RPC, stream and game event leaves a line tied to one `request_id`.
Operators read and filter these logs ([Operations](../operations/README.md)); this page says what a line holds and never holds.
The code is in `backend/internal/platform/logging`, `platform/rpclog` and `platform/httpserver`.

## Fields

| Field | When | What it is |
| --- | --- | --- |
| `time`, `severity`, `message` | Always | The time, the level (`DEBUG`, `INFO`, `WARNING`, `ERROR`: the Cloud Logging names) and a fixed text per code point. Never user text. |
| `service`, `version` | Always | `meurpg-api` and the build version (the same as `SystemService.GetServerInfo`). |
| `request_id` | Inside a request | 32 hexadecimal characters, generated by the server. |
| `user_id` | With a valid session | The account ID, a UUID. |
| `campaign_id` | When the request is about a campaign | The campaign UUID. Only a value already parsed as a UUID enters, because the client chooses it. |
| `logging.googleapis.com/trace` | On Cloud Run, with `GOOGLE_CLOUD_PROJECT` | `projects/<project>/traces/<id>`, from the `X-Cloud-Trace-Context` header, so Cloud Logging joins a request's lines. |

A `slog` handler adds `request_id`, `user_id` and `campaign_id` to every line written with a context (`logger.InfoContext(ctx, ...)`).
Code that logs without a context does not carry them, which is why request code always passes `ctx`.

## The request id

The server generates the id, puts it in the context and returns it in the `X-Request-Id` header.
An `X-Request-Id` the client sends is ignored: otherwise anyone could write what they liked into the log or pose as another request.
The app can read the header because the API and the app share an origin, so whoever sees an error can quote the id.

`user_id` and `campaign_id` are learned after the id, deeper in the call, so the context holds a pointer to the fields.
The session interceptor records the user, `authz` and the log interceptor record the campaign, and the `http request` line, written last by the outer layer, already sees them.

## Lines

| `message` | Level | Fields besides the common ones |
| --- | --- | --- |
| `http request` | `INFO`; `WARNING` for a 5xx status; `DEBUG` for `/healthz` and `/readyz` | `method`, `path` (without the query, cut at 256 bytes with `...[truncated]`), `proto`, `status`, `duration_ms` |
| `rpc` | `DEBUG` for `ok` and for the outcomes a caller causes (`invalid_argument`, `not_found`, `permission_denied`, `failed_precondition`, `already_exists`, `aborted`, `unauthenticated`, `resource_exhausted`, `out_of_range`, `canceled`); `ERROR` for the rest, except the `unavailable` of an idle instance's stream (`INFO`) | `procedure`, `code`, `duration_ms`, `stream`; and when the code is not `ok`: `error` and, when the error carries a typed detail, `reason` |
| `stream opened`, `stream closed` | `DEBUG` | `procedure`; at the end `duration_ms`, `messages` (sent) and `close_reason` (`client_gone`, `server_ended`, `access_lost`, `instance_idle`, `error`) |
| `event` | `DEBUG` | `event` (`<area>.<past_verb>`), only IDs and closed enums |

The `rpclog` interceptor is first in the chain, so it is outermost and sees the final error wherever it came from.
`reason` is the reason enum of the error detail (`XPBlocked`, `CharacterBlocked`...), read by reflection from the field whose name contains `reason`, so a new detail appears without touching the interceptor.
The `close_reason` of a stream the server ends by itself (the session ended, the lifetime cap, shutdown) is always `server_ended`: from inside, the three are the same fact.
A stream an instance ends because it no longer receives calls (a deploy) has the close reason `instance_idle`, and its `rpc` line is `INFO`, not `ERROR`: the client gets `unavailable` and reconnects, and it is no failure of the release.

The `error` text stays only in the log.
A handler that returns a non-Connect error (a driver message, a file path) would have it sent to the client as `unknown`; the interceptor swaps it for `internal` with a fixed sentence and the real text goes to the `rpc` line.
Connect error messages, which the client also receives, are fixed sentences; the log cuts them at 500 characters.
Rate-limit refusals and database error classes have their own `WARN` and `ERROR` lines ([API](api.md)).

## Game events

An `event` marks a state change that was just written.
It is logged by `logging.Event(ctx, logger, name, attrs...)` after `db.InTx` returns, so a retried transaction (`40001`) does not log twice.
Attributes are IDs (`session_id`, `encounter_id`, `character_id`, `combatant_id`, `map_id`, `point_id`, `puzzle_id`, `award_id`, `entry_key`...) and closed enums (`outcome`, `kind`, `mode`, `reason`).

| Area | Events (prefix) |
| --- | --- |
| Session | `session.` |
| Combat | `combat.`, with one event per kind of combat change; all of combat goes through one function (`write`, `play/combat_write.go`) |
| Rests | `rest.`, `hit_dice.` |
| Scene | `scene.` |
| Puzzle | `puzzle.` |
| Trap and treasure | `trap.`, `treasure.` |
| XP | `xp.`, `levelup.` |
| Table content | `content.` |
| AI images | `image.` |
| Campaign and character | `invite.`, `character.` |

The list of names is the code: `grep -rn 'logging.Event' backend/internal`.

## What never goes in the log

Session, invite, claim, login and CSRF tokens; cookies; the OIDC client secret; `GEMINI_API_KEY`; e-mails; display, character, NPC and campaign names; any text a person typed (documents, notes, clues, prompts, content entries); request or response bodies; headers; the URL query; the client IP.
Only IDs and closed enums.
The reasons are RN-10 (a player must not learn what the master hid, and the log reaches more people than the app) and the LGPD ([Privacy](../privacy.md#api-logs)).

A guard in the handler enforces this even when a code point errs: it drops every attribute whose name is `email`, `token`, `password`, `secret`, `cookie`, `authorization`, `prompt`, `body`, `text`, `name` or `display_name`, at any depth (inside groups and maps), case-insensitively (`TestDenyListDropsKeysAtAnyDepth`).
The guard is the safety net, not the plan: code logs IDs.

## Levels

`LOG_LEVEL` (`debug`, `info`, `warn`, `error`) picks the level; the default is `info`, which production uses until someone raises it.
At `info` the cost is one line per request plus the RPC error lines.
At `debug` the `rpc`, `stream` and `event` lines also appear.
The local environment (`make up`, Docker or native) starts at `debug`; `LOG_LEVEL=info make up` lowers it.
The native stack's log is `~/.meurpg/run/api.log`.
